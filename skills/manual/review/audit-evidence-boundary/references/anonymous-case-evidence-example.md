# Anonymous Case Evidence Example

This example shows how to turn private AI coding audit material into a public-safe report without inventing evidence.

## Input situation

A reviewer inspected an AI-generated React state refactor. The private workspace contains an agent log, a diff, and a focused reducer test failure. The organization name, private branch, hostnames, and user-specific paths cannot be published.

## Evidence ledger

| Claim | Class | Required proof | Public-safe summary | If missing | Owner / next action |
| --- | --- | --- | --- | --- | --- |
| The audit covered a React state refactor | Fact | PR diff or agent log showing touched state files | `Reviewed a React state-management refactor generated by an AI agent` | Downgrade to method sample | Reviewer keeps source note privately |
| The highest risk is error state being overwritten | Inference | diff hunk plus failing focused test or reviewer quote | `Top risk: error state can be hidden by a later loading transition` | Mark as suspected risk | Add focused reducer test or maintainer confirmation |
| The focused reducer test failed | Fact | command, exit code, and key failure line | `Focused reducer test failed on the error branch` | Do not write `Fail means`; write `Next evidence needed` | Run the smallest related test again |
| The change caused a production incident | Stop | incident record and permission to publish | Do not publish | Remove the claim entirely | Ask for explicit authorization or omit |
| The review improved team velocity | Unverified | approved metric, quote, or before/after cycle time | `No outcome metric yet` | Do not imply result | Collect follow-up data after delivery |

## Public-safe paragraph

```markdown
In this anonymous AI coding audit, the reviewed artifact was a React state-management refactor generated by an AI agent. The strongest publishable evidence was a focused reducer test failure on the error branch, so the report treated "error state can be hidden by a later loading transition" as the top risk. No customer name, private path, hostname, branch name, or internal ticket ID is included. There is no claim about production incidents or velocity improvement because those claims were not supported by publishable evidence.
```

## Decision

- `Continue`: publish a narrow technical case if authorization covers the redacted artifact and the focused failure can be summarized safely.
- `Narrow`: publish only the command-ladder lesson if customer permission or broader context is unclear.
- `Stop`: do not publish if redaction removes the command result or if the only interesting claim depends on private incident data.
